1. Resumen ejecutivo

InmobiliariasCloud es una SPA en React para un catálogo inmobiliario, apoyada en dos microservicios Spring Boot, dos proveedores de identidad (Azure Entra ID para el staff y Amazon Cognito para los clientes), un API Gateway HTTP como única puerta de entrada, PostgreSQL como estado y dos brokers con roles distintos: Kafka para el flujo de eventos de la lista de deseos y RabbitMQ para las tareas del informe PDF.

Estado de la verificación (17-11-2026). Se probaron en vivo los cinco riesgos de la rúbrica. Cuatro pasaron sin observaciones. El quinto (transacción pública que expone datos sensibles) se detectó y se corrigió: el catálogo público devolvía el correo corporativo y el objectId de Entra de quien publicó. Hoy esos campos ya no se serializan y existe un test que lo impide.

4. Camino de una petición autenticada

  1. El navegador obtiene un access token (MSAL para staff, Cognito para clientes).
  2. Lo envía como Authorization: Bearer <token>.
  3. API Gateway descarga el JWKS del emisor y valida firma, iss, aud, exp y scope.
  4. Si el token es válido, sobrescribe las cabeceras X-User, X-User-Oid, X-User-Name (y X-User-Rol en Cognito) con los claims. El valor que mande el navegador se descarta.
  5. La integración HTTP_PROXY reenvía la petición por el VPC Link al NLB y al microservicio.
  6. El IdentidadInterceptor resuelve el rol de negocio y aplica la matriz de permisos.
  7. El microservicio responde y API Gateway agrega las cabeceras CORS.
Regla de oro: la autenticación (¿el token es válido?) la hace API Gateway; la autorización (¿este rol puede?) la hace el microservicio. Por eso un 401 y un 403 significan cosas distintas y se pueden demostrar por separado.

6.2 Flujo en el navegador (MSAL)

  1. El usuario pulsa “Ingresar” y MSAL lo redirige a Entra ID.
  2. Entra autentica y devuelve el código; MSAL lo canjea por tokens.
  3. La sesión se guarda en sessionStorage, no en localStorage: al cerrar la pestaña desaparece.
  4. Antes de cada llamada, obtenerAccessToken() pide un token con scopes: [API_SCOPE] (usa la caché si sigue vigente).
  5. El token viaja como Authorization: Bearer ....

6.4 Resolución del rol

El microservicio compara la identidad recibida con la configuración de application-prod.yml:

autorizacion-requerida: true
admin-email: administrador@inmobiliariaduoc.onmicrosoft.com
admin-oid:   5ce11c6e-c796-41eb-b8ed-1872878cd197
corredor-email: Corredor@InmobiliariaDuoc.onmicrosoft.com
corredor-oid:   0a73de94-2722-4221-836c-bd7f3af16980
  • Coincide con admin (correo u oid) → ADMIN.
  • Coincide con corredor → CORREDOR.
  • Cualquier otra cuenta Entra válida → PUBLIC: puede ver el catálogo, nada más.
Por qué se acepta el oid: el correo puede cambiar (matrimonio, alias, mayúsculas). El objectId es estable y lo trae siempre el access token de Entra. Aun así, la comparación de correo se hace case-insensitive.

7.2 Trigger Pre Token Generation V2_0

Una Lambda (inmobiliarias-cliente-rol) agrega los claims rol=CLIENTE, email y name al token. Se usa V2_0 y no V1_0 porque V1_0 solo personaliza el ID token, y API Gateway valida el access token.

// Salida del trigger (resumida)
exports.handler = async (event) => {
  event.response = {
    claimsOverrideDetails: {
      claimsToAddOrOverride: {
        rol: 'CLIENTE',
        email: event.request.userAttributes.email,
        name: event.request.userAttributes.name || ''
      }
    }
  };
  return event;
};

7.3 Por qué el scope aws.cognito.signin.user.admin

El access token y el ID token de Cognito comparten iss y aud. Sin una distinción, el authorizer aceptaría ambos. El scope solo existe en el access token, así que exigirlo en las rutas de cliente hace que un ID token reciba 403 de API Gateway. Es la barrera que impide usar el token equivocado.

7.4 SRP y la corrección del storage

El login usa SRP: el navegador demuestra conocimiento de la contraseña sin enviarla. El SDK amazon-cognito-identity-js crea un CognitoUser que no hereda el storage del pool. Como el pool usa sessionStorage, hay que pasarlo explícitamente:

const usuario = new CognitoUser({ Username: email, Pool: userPool, Storage: userPool.storage });
Bug real que costó depurar: sin Storage: userPool.storage, el login guardaba los tokens en localStorage y getCurrentUser() (que lee sessionStorage) no encontraba la sesión: el usuario “entraba” pero la app lo mostraba deslogueado. Si alguien toca ese archivo, debe conservar esa línea.

7.5 Flujo completo del cliente

  1. Registro: correo + contraseña → Cognito envía un código.
  2. Confirmación: el usuario ingresa el código → la cuenta queda confirmada.
  3. Login SRP: Cognito devuelve access, ID y refresh token.
  4. Llamadas: /api/cliente/** con el access token.
  5. Refresh: cuando el access token expira, se renueva con el refresh token (30 días).
  6. Logout: se revoca el refresh token y se limpian las claves del storage.

9.2 CORS

  • Orígenes exactos: producción y desarrollo; nunca *.
  • Headers permitidos: Authorization, Content-Type, Accept. Las X-User* no se permiten: el navegador no debe poder inyectarlas.
  • AllowCredentials: false: se usa Bearer, no cookies, lo que reduce la superficie CSRF.
  • Preflight cacheado 3600 s.
Lección real: cuando una ruta no existe, API Gateway responde 404 sin cabeceras CORS y el navegador muestra “blocked by CORS policy”. La causa no era CORS sino la ruta faltante. La forma de distinguirlo es simple: una ruta existente sin token devuelve 401 con access-control-allow-origin.

9.3 Inyección de identidad

RequestParameters:
  overwrite:header.X-User:      $context.authorizer.claims.preferred_username
  overwrite:header.X-User-Oid:  $context.authorizer.claims.oid
  overwrite:header.X-User-Name: $context.authorizer.claims.name

La acción overwrite es deliberada: si el navegador envía X-User: administrador@..., API Gateway lo descarta y escribe el claim real. En las rutas de cliente se agrega rol.

9.4 VPC Link, NLB y Security Groups

Los microservicios escuchan en 0.0.0.0 dentro del contenedor, pero el Security Group solo permite 8081/8082 desde el CIDR de la VPC. El único cliente legítimo es API Gateway a través del VPC Link y los NLB internos. Verificado: desde internet, http://54.88.89.184:8081 y :8082 no responden.

9.5 Cómo se actualiza

  1. Se edita backend/aws/api-gateway.yaml.
  2. En CloudShell se crea un change set reutilizando los parámetros actuales.
  3. Se revisa el diff (por ejemplo, solo dos Add para las rutas de avisos).
  4. Se ejecuta y se espera wait stack-update-complete → UPDATE_COMPLETE.
Por qué CloudShell: es la única vía del proyecto con credenciales AWS. GitHub Actions construye imágenes, pero no aplica CloudFormation.

11.3 Flujo A: alta de propiedad → novedades agrupadas

  1. POST /api/propiedades guarda la propiedad y publica el evento con key = comuna.
  2. PropiedadNuevaNotificador busca las alertas de esa comuna y crea una fila en wishlist_novedades por usuario afectado (resumenId = null).
  3. ResumenNovedadesService agrupa: si el usuario acumula 6 pendientes (NOTIF_UMBRAL), crea un resumen con las 6 más antiguas; además, un cron diario a las 20:00 (NOTIF_CRON, America/Santiago) agrupa lo que quede.
  4. Publica NotificacionSistemaEvent en notificaciones-sistema con key = email.
  5. NotificacionDispatchConsumer envía un solo correo con el resumen y hace ACK.
  6. El frontend consulta GET /api/cliente/novedades y muestra una alerta por resumen, con detalle desplegable.
Anti-spam por diseño: no se manda un correo por propiedad. Se agrupan por umbral o por barrido diario.

11.4 Flujo B: baja de propiedad → aviso y limpieza de favoritos

  1. DELETE /api/propiedades/{id} registra auditoría, publica PropiedadEliminadaEvent antes de borrar (necesita título, tipo de operación y comuna) y luego elimina la propiedad.
  2. wishlist-service consume con el grupo wishlist-bajas-group.
  3. AvisoService.registrarEliminacion ejecuta en una sola transacción: busca los favoritos por propiedadId, crea un aviso por usuario afectado (si no existe, por la restricción única) y borra los favoritos de esa propiedad.
  4. El texto se arma según tipoOperacion: “ya fue vendida” / “ya fue arrendada” / “ya fue vendida o arrendada”, siempre seguido de “y se eliminó automáticamente de tus favoritos.”
  5. Home.jsx y Cliente.jsx sondean cada 15 s: el favorito desaparece y aparece la alerta. El botón “Entendido” llama a DELETE /api/cliente/avisos/{id}.
Por qué es asíncrono: la baja no debe fallar porque Kafka esté caído (el publicador no relanza). El costo es consistencia eventual: el favorito puede tardar hasta 15 s en desaparecer de la vista; el backend ya quedó consistente en milisegundos.

11.5 Semántica e idempotencia

  • At-least-once: Kafka puede reentregar. Por eso el aviso tiene restricción única (usuario_email, propiedad_id) y se verifica con existsBy... antes de insertar.
  • Orden por clave: todos los eventos de la misma comuna van a la misma partición.
  • Relectura: la retención de 7 días permite reprocesar si un consumidor estuvo caído.
  • DLQ: un mensaje veneno no bloquea la partición; se publica en <topic>.dlq.

11.6 Por qué Kafka aquí y no RabbitMQ

Se necesita registro de eventos, particiones por comuna, varios consumidores independientes y posibilidad de releer. RabbitMQ en cambio está pensado para tareas puntuales que se consumen y desaparecen.

16. Resiliencia y patrones

  • Desacoplamiento asíncrono: el catálogo no espera al wishlist ni a Rabbit; responde rápido.
  • Degradación elegante: si Rabbit está caído, el catálogo sigue funcionando; si Kafka falla al publicar una baja, el DELETE igual se completa.
  • Reintentos con backoff exponencial (3 intentos, 2 s × 2) y DLQ para no perder mensajes irrecuperables.
  • Idempotencia: restricciones únicas y existsBy... evitan duplicar avisos si Kafka reentrega.
  • Orden por clave: comuna en altas y bajas, correo en notificaciones.
  • Consistencia eventual + polling en la interfaz.
  • Healthchecks y restart: unless-stopped en todos los contenedores.
  • Transacciones para operaciones compuestas (crear aviso + borrar favorito).
Limitación honesta: si Kafka está caído en el momento exacto de un alta o baja, el evento de ese instante se pierde (solo queda el error en el log). La mitigación de producción sería el patrón outbox con reintento, o publicar dentro de la misma transacción a una tabla de salida.

19. Preguntas de defensa

¿Por qué dos proveedores de identidad?

Porque los públicos son distintos. Los empleados ya existen en el directorio corporativo (Entra ID, con gobierno de cuentas y bajas centralizadas); los clientes deben autoregistrarse sin intervención. Mezclarlos obligaría a crear cuentas corporativas para clientes o a implementar registro y recuperación de contraseña propios.

¿Por qué API Gateway valida el token y el microservicio autoriza?

Separación de responsabilidades. La validación criptográfica (firma, JWKS, exp, iss, aud) es infraestructura y API Gateway la hace sin Lambda. Los roles del negocio son dominio y cambian con las reglas de la empresa. Además, API Gateway no puede devolver un 403 con un cuerpo JSON propio.

¿Qué diferencia hay entre access token e ID token?

El access token es la credencial para la API: lleva scope y aud de la API. El ID token describe al usuario para la aplicación. Aquí las rutas exigen un scope que solo está en el access token, justamente para rechazar el ID token.

¿Por qué el scope aws.cognito.signin.user.admin?

Porque es el claim que distingue el access token del ID token en Cognito. Sin esa línea, el authorizer aceptaría ambos, ya que comparten issuer y audiencia. Con la línea, el ID token recibe 403.

¿Qué pasa si Kafka está caído?

El alta o la baja se completa igual: la publicación es asíncrona y el error solo queda en el log. Se pierde el evento de ese instante; las novedades o avisos de ese cambio no se generan hasta que se reprocese. Para producción se mitigaría con el patrón outbox y reintento.

¿Qué pasa si RabbitMQ está caído?

El catálogo y las rutas siguen funcionando. La solicitud de informe falla al publicar y el RabbitTemplate reintenta la conexión. El contenedor arranca igual porque el depends_on usa service_started, no service_healthy.

¿Por qué una DLQ y no reintentar infinito?

Un mensaje “veneno” bloquearía la cola o la partición. Con reintentos acotados y DLQ se preserva el mensaje para análisis y el sistema sigue fluyendo. En Rabbit la DLQ expira a los 10 minutos para no acumular basura.

¿Cómo evitas avisos duplicados si Kafka reentrega?

Con una restricción única (usuario_email, propiedad_id) en wishlist_avisos y una verificación existsBy... antes de insertar. Además, la creación del aviso y el borrado del favorito ocurren en una sola transacción.

¿Por qué el favorito tarda hasta 15 segundos en desaparecer?

Porque la baja es asíncrona (Kafka) y la interfaz sondea cada 15 segundos. El backend queda consistente en milisegundos; el retraso es solo de presentación. Se podría sustituir el polling por SSE o WebSocket.

¿Por qué el texto dice “vendida” o “arrendada”?

Se usa tipoOperacion de la propiedad. Si es Venta dice “ya fue vendida”; si es Arriendo, “ya fue arrendada”; cualquier otro valor usa el genérico “ya fue vendida o arrendada”.

¿Por qué una sola base de datos para dos microservicios?

Simplicidad del laboratorio y transacciones locales. Cada servicio accede solo a sus tablas (bajo acoplamiento). En producción se evaluaría database-per-service y comunicación por eventos.

¿Por qué exactamente 2 colas de Rabbit y 2 DLQ?

Es el requisito de la rúbrica: dos colas de trabajo (correos y PDF) con su DLQ. La tercera cola original se eliminó y la auditoría pasó a ser síncrona a la base, que además da consistencia inmediata.

¿Por qué X-User es confiable?

Porque la escribe API Gateway con acción overwrite después de validar el token. Cualquier valor enviado por el navegador se descarta. Se demostró enviando X-User: administrador a una ruta protegida: la respuesta fue 401.

¿Qué pasó con el error de CORS de los avisos?

La ruta /api/cliente/avisos no existía. API Gateway devolvía 404 sin cabeceras CORS y el navegador lo mostraba como error de CORS. Se aplicó un change set que creó las dos rutas y el GET pasó a 401 con CORS (y luego a 200 con token).

¿Qué encontraron al revisar los datos sensibles?

El catálogo público devolvía creadoPorEmail y creadoPorOid del staff. Se ocultaron con @JsonIgnore y se agregó un test de regresión. El frontend nunca usó esos campos, así que no hubo impacto funcional.

¿Por qué el catálogo devuelve imágenes en base64?

Es una decisión de simplicidad del laboratorio: la imagen se guarda como data:image/...;base64 en la tabla. Funciona, pero infla la respuesta (el catálogo pesa cerca de 2 MB). La mejora sería guardar archivos y servir una URL, o usar object storage.
